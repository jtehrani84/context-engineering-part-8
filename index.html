Context Engineering Series · Part 8

From the Evolving Harness
to the Frontier Harness

Part 7 proved a guard could grade my writing. Part 8 asks the harder question it left open... what stops a guard the agent can simply switch off for itself? The answer isn't a smarter guard. It's custody: a human who isn't the agent holds the key. Then that one idea travels across three runtimes.

26 components· 434 automated checks· two adversarial passes + a fuzzer catch, ~28 real defects fixed· one core, three runtimes

The Wall Part 7 Left Standing

Part 7 ended on a wall I couldn't argue my way past. I'd built a detector that catches generic AI writing well, and it does. But when I pointed a model at imitating me specifically, the detector lost... it scored a deliberate mimic as more me-than-me. No better detector fixes that, because the answer was never in the text. Whether something is authentically mine is a question of provenance... who actually typed it. A detector can improve forever and still never answer that one.

That sounds like a dead end, and for authorship it mostly is. But it turned out to be the most useful thing Part 7 taught me, because the same shape shows up one level up... in the guard itself.

Custody, Not Typing

Here's the move. A guard the agent can approve for itself, disable, or quietly rewrite is theater. It's the mimic grading its own mimic, exactly the failure Part 7 named, wearing a different coat. So the guard can't be something the agent installs. Its trust root has to be held by a human who is not the agent.

The mechanics are smaller than the idea. I hold a secret the agent never sees, and I pin a fingerprint of the safety files myself. When I switched the core on, the agent that wrote every line of it was structurally unable to do that one step for me. It guided, I turned the key. Custody, not typing.

Voice Was Only the First Failure Class

The voice checker was never really about voice. It was one instance of a pattern: a deterministic test for a specific way work goes wrong, wired to block, honest about its ceiling. Once I saw it that way, the interesting question became what else has that shape.

Plenty, it turns out. An agent doesn't only risk sounding like a robot. It can be talked into something by a poisoned input it was only supposed to read. It can leak data on the way out, sometimes through a channel nobody thinks of as "sending." It can fire an action nobody approved, or leave a record you can't actually trust. Each of those is a failure class, and each gets the same treatment the voice tell got: a check that fires on the bad case, stays quiet on the good one, and says plainly what it can't catch.

One Core, Three Runtimes

A layer that only works inside one tool is really just a feature of that tool. So the checks live in a single host-neutral core, and each runtime reaches them through a thin adapter that translates the tool's own events into one shared vocabulary. The same poisoned-input check, the same egress guard, the same tamper-evident record, whether the work happens in an agentic coding CLI, an open-source coding agent, or a managed enterprise execution runtime.

The way I keep myself honest about "the same" is a conformance test: for an equivalent operation, all three adapters have to produce identical canonical events. If they diverge, that's a bug in an adapter, not a difference I get to wave away.

Reconciled Against the Real Thing

The obvious question about any layer like this is whether it's real or a diagram. So I didn't model the adapters against how I imagined each tool worked. I read each product's actual installed interface and reconciled against it, which immediately caught things my guess got wrong.

Honest boundary on that word "reconciled": I verified the adapters against each product's real interface, and that's a real step past a mock. It is not the same as watching them fire inside a live session. That last mile is named in the limits below, not hidden.

It Attacked Its Own Code

A guard you only tested on the happy path is a guard you haven't tested. The egress control came straight out of a real, public attack class: an agent reads a poisoned record, and data walks out the door inside a URL that a rendered image quietly resolves... no click, no obvious "send." So I built the guard to treat any resolvable URL as a way out, not just the ones that look like sending.

Then I turned the same adversarial process on the harness itself. Two passes, each one trying to break what the last one built, and then a fuzzer that went after what both of them missed. Together they found and fixed roughly 28 real defects in the harness's own code... including one in the egress guard I'd written specifically to stop that attack, which had its own version of the exact bug it was meant to catch.

That last one is the point. The whole thesis is that you don't trust the thing to grade itself, so running the thesis on the harness meant the harness got caught too, before any of it was switched on. That's what earns a gate its trust... it fires on cue, and I've tried hard to break it, and it held.

Where This Is Thin

The checks only catch what I taught them. A determined attacker who knows a specific guard exists can study it and route around it... which is precisely the ceiling Part 7 named for the voice detector, now the honest ceiling for the whole layer. I raise it over time. I don't get to declare it finished.

Verified against the interface is not the same as watched in flight. All three adapters were reconciled against the real installed APIs, and that caught real bugs. But a live in-host capture... a real session, watched end to end, with the controls observed actually firing... hasn't run yet. So far the controls are proven in tests and haven't been seen live inside a running host.

One owner with the key is still one owner. A single person holds the trust root, and until a separate hardening step runs, tampering with the safety files gets detected without being physically prevented at the OS level. The managed runtime is also observe-only by nature, so enforcement there lives on the platform side. Both of those are disclosed here, and neither is solved yet.

So What, Then: What Portability Buys

You can't own the frontier model. You rent it, and it changes under you every few months. So the durable thing was never going to be the model. It's everything wrapped around it: the checks that catch how the work goes wrong, the evals that say whether the output is any good, the record of what actually happened, and the custody that decides who's allowed to change any of it.

Part 7 showed that layer can evolve itself while the model underneath stays frozen. Part 8's addition is that the layer travels. The same core, the same custody, the same honest ceiling, running across whichever runtime the work happens in... and unlike the model you rent, that's yours to keep. And it isn't only my claim... NVIDIA's SoL-Pi built a set of harness improvements on one model and carried them to another with no retraining, the same bet running in someone else's lab.

This is proven, not shipped to production, and it's a first honest draft of the argument, not the last word. If you build agents that touch anything you'd mind losing, I'd rather you poke at where it's thin than take it on faith.
